## 1. 프로젝트 개요

### 1.1 배경
순환보직제를 운영하는 공직 사회의 특성상, 담당자는 2~3년 주기로 전혀 다른 업무를 맡게 됩니다. 이때 가장 큰 시간 낭비 요인은 "전임자가 남긴 자료를 이해하는 데 드는 시간"입니다. 전임자의 PC와 공유폴더에는 보통 다음과 같은 문제가 있습니다.

- 파일명 규칙이 사람마다 제각각 (`최종`, `최최종`, `진짜최종_수정2` 등)
- 폴더 구조가 업무 흐름이 아니라 개인 습관대로 구성됨
- 같은 문서의 여러 버전이 중복 저장되어 어느 것이 최신인지 알 수 없음
- 문서 내용을 열어보기 전까지는 무슨 자료인지 파악 불가
- HWP, DOCX, XLSX, PPTX, PDF, 이메일 첨부파일 등 포맷이 혼재

### 1.2 목적
전임자 PC/공유폴더의 파일을 스캔하여 **제목·생성(수정)일시·내용**을 기준으로 자동 정리하고, 로컬 LLM(Ollama + Gemma 모델)을 활용해 문서를 요약·분류·검색 가능하게 만들어, 신임자의 업무 파악 시간을 대폭 단축하는 것을 목적으로 합니다.

### 1.3 기대 효과
| 효과 | 설명 |
|---|---|
| 업무 인수 시간 단축 | 자료 파악에 걸리는 시간을 수 주 → 수 일로 단축 |
| 지식 단절 방지 | 담당자 교체 시마다 반복되는 "노하우 유실" 완화 |
| 표준화 | 부서/기관 차원의 자료 정리 방식 표준 확립 |
| 감사·점검 대응력 향상 | 과거 문서를 빠르게 검색해 근거 자료 제시 가능 |
| 보안성 | 외부 클라우드 AI를 쓰지 않고 로컬에서만 처리 → 공공기관 망분리 환경에 적합 |

### 1.4 핵심 사용자 (페르소나)
- **주 사용자(신임자)**: 새 부서에 발령받아 전임자 자료를 파악해야 하는 담당자
- **보조 사용자(전임자)**: 이임 전 자료를 정리·인계해야 하는 담당자
- **부가 사용자(부서 관리자)**: 부서 전체의 문서 자산을 표준화하고 감사 대응 자료를 관리하는 팀장/과장

| R2 | 파일 제목, 생성일시, 수정일시, 확장자, 크기, 경로를 인덱스 DB에 저장 | Must |

| R5 | 유사/중복 파일 탐지 및 최신본 추정 | Should |
| R6 | 제목·날짜·카테고리·키워드 기반 검색 및 자연어 질의(RAG) | Should |
| R7 | 자동 분류 결과를 사람이 검수/수정할 수 있는 UI 제공 | Must |
| R8 | 정리된 자료를 바탕으로 "인수인계서 초안" 자동 생성 | Should |
| R9 | 개인정보·민감정보 포함 문서 자동 탐지 및 경고/마스킹 | Should |
| R10 | 완전 오프라인(폐쇄망) 환경에서 동작, 외부 서버 전송 없음 | Must |
| R11 | 분류 규칙(사용자 정의 태그, 폴더 매핑) 커스터마이징 | Could |

> 공직 문서 특성상 **HWP(한글) 처리**와 **완전 오프라인 동작**이 이 시스템의 성패를 가르는 두 가지 핵심 제약입니다.

## 3. 핵심 기능 상세 설계

### 3.1 파일 수집 모듈 (Ingestion)
- 지정 경로(로컬 폴더, 이동식 디스크, 네트워크 공유폴더 UNC 경로) 스캔
- 스캔 시 제외 규칙 설정 가능 (임시파일 `~$*`, 시스템 폴더, 특정 확장자 제외)
- 증분 스캔 지원: 최초 전체 스캔 후 변경분만 재스캔 (파일 해시 비교)
- 스캔 진행률 표시 및 대용량 폴더(수만 건) 처리 시 백그라운드 처리

### 3.2 메타데이터 추출 및 인덱싱
추출 항목: 파일명, 경로, 확장자, 크기, 생성일시, 수정일시, 접근일시, 파일 해시(SHA-256, 중복탐지용), 작성자(문서 속성에 있는 경우)

파일시스템의 "생성일시"는 파일 복사 시 리셋되는 경우가 많으므로, **문서 내부 메타데이터(작성일, 최종 수정자)**를 우선 신뢰하고 파일시스템 값은 보조 지표로 사용하는 로직이 필요합니다.

### 3.3 문서 파싱 엔진
| 포맷 | 처리 방식 |
|---|---|
| HWP/HWPX | HWP 전용 파서(hwp5, pyhwp 계열) 또는 한글과컴퓨터 API/OLE 자동화로 텍스트 추출 |
| DOCX | python-docx 등으로 본문·표·머리글 텍스트 추출 |
| XLSX/CSV | 시트별 셀 데이터 요약, 표 구조를 텍스트로 변환 후 LLM에 전달 |
| PPTX | 슬라이드별 텍스트, 노트 추출 |
| PDF | 텍스트 레이어 추출, 스캔본은 OCR(Tesseract 등 한글 지원 엔진) 병행 |
| 이미지(JPG/PNG 등) | OCR로 텍스트화 (회의록 사진, 스캔 문서 대응) |
| 이메일(.eml/.msg) | 본문·첨부파일 분리 추출 |

### 3.4 로컬 LLM 분석 모듈 (Ollama + gemma4:e2b)
경량 모델(E2B)의 특성을 고려하여 **한 번에 하나의 명확한 작업**만 요청하는 프롬프트 설계가 중요합니다.

- **문서 요약**: 각 문서를 2~3문장으로 요약해 인덱스에 저장 (목록에서 미리보기로 표시)
- **자동 분류/태깅**: 문서를 부서 업무 특성에 맞는 카테고리(예: 예산, 인사, 감사, 회의록, 계약, 민원)로 자동 분류
- **키워드 추출**: 검색 정확도를 높이기 위한 핵심어 추출
- **버전/최신본 추정**: 파일명과 내용 유사도를 함께 활용해 "이 5개 파일 중 최신본은 이것으로 추정됨"을 제안
- **민감정보 탐지**: 주민등록번호, 전화번호, 계좌번호 등 패턴을 정규식+LLM으로 탐지해 경고 표시 (마스킹은 자동 삭제가 아니라 "주의 표시" 수준으로, 오탐 시 문서 훼손 방지)
- **RAG 기반 질의응답**: "작년 예산 관련 자료 어디 있어?" 같은 자연어 질문에 관련 문서를 찾아 답변 (임베딩 모델 + 벡터 검색 필요, gemma4:e2b는 답변 생성만 담당하고 검색은 별도 벡터 DB가 수행)

> 처리 속도 관리를 위해 LLM 분석은 **선택적/백그라운드 작업**으로 설계하고, 사용자가 "전체 분석" 또는 "이 폴더만 분석"을 선택할 수 있게 해야 합니다. 수만 건 전체를 동시에 LLM에 넣으면 저사양 공무원 PC에서는 매우 느릴 수 있습니다.

### 3.5 자동 정리 엔진
- 규칙 기반(파일 확장자, 날짜) + AI 기반(내용 분류)의 하이브리드 정리
- 정리 방식 3가지 제공: **날짜별**(연도/월), **카테고리별**(업무 분류), **하이브리드**(카테고리 > 연도)
- "정리 미리보기" 화면에서 자동 제안된 이동 계획을 사람이 확인 후 승인해야 실제 파일 이동/복사 실행 (원본 폴더 구조는 백업 유지 옵션 제공 — 실수로 인한 자료 유실 방지가 최우선)
- 실제 파일 이동은 기본적으로 **복사(원본 보존)** 방식을 기본값으로 하고, 이동은 명시적 옵션으로만 제공

### 3.6 검색/탐색
- 키워드 검색(파일명 + 본문 + 태그 통합 검색)
- 필터: 기간, 카테고리, 파일형식, 작성자
- 타임라인 뷰: 특정 기간에 어떤 문서가 생성되었는지 시각적으로 확인 (업무 흐름 파악에 유용)
- 자연어 질의: "2024년 감사 지적사항 관련 문서 찾아줘" 같은 질문 처리

### 3.7 인수인계서 자동 초안 생성 (차별화 포인트)
정리·분석이 끝난 자료를 바탕으로 표준 인수인계서 양식(업무 개요, 주요 현안, 연간 업무 일정, 주요 문서 목록, 담당자 연락처 등)의 **초안**을 자동 생성. 신임자는 이를 검수·보완만 하면 되므로 작성 부담이 크게 줄어듭니다. 생성 결과는 HWP/DOCX로 내보내기 지원(공직 사회 표준 포맷 고려).

### 3.8 보안 및 개인정보 처리
- 100% 로컬 처리, 인터넷 연결 불필요 (망분리 환경 대응)
- 문서 원문은 외부로 전송되지 않으며, LLM도 로컬(Ollama)에서만 구동
- 민감정보 탐지 로그는 별도 관리자만 접근 가능하도록 접근 제어
- 프로그램 자체는 업무망 반입 시 보안 심사를 통과해야 하므로, 오프라인 설치 패키지(인터넷 연결 없이 설치 가능) 형태로 배포 설계 필요

## 4. 시스템 아키텍처

### 4.1 아키텍처 원칙
1. **로컬 우선(Local-First)**: 모든 데이터와 연산이 사용자 PC 내부에서 처리
2. **오프라인 동작**: 설치 후 인터넷 연결 없이 전체 기능 구동 가능
3. **비파괴적 처리**: 원본 파일은 기본적으로 읽기 전용으로 취급, 정리는 복사본에 적용

### 4.2 계층 구조
```
┌─────────────────────────────────────────┐
│  UI Layer (데스크톱 앱, Electron 기반)      │
│  대시보드 / 탐색기 / 검색 / AI채팅 / 인계서   │
├─────────────────────────────────────────┤
│  Application Layer                       │
│  스캔 오케스트레이터 / 분류 엔진 / 정리 엔진  │
├─────────────────────────────────────────┤
│  AI Layer                                │
│  Ollama (gemma4:e2b)  +  임베딩모델 +     │
│  프롬프트 템플릿 관리                       │
├─────────────────────────────────────────┤
│  Data Layer                              │
│  SQLite(메타데이터) + 벡터DB(임베딩,검색)   │
├─────────────────────────────────────────┤
│  File Parsing Layer                      │
│  HWP/DOCX/XLSX/PPTX/PDF/OCR 파서 모듈군   │
└─────────────────────────────────────────┘
             ↓
     로컬 파일시스템 / 네트워크 공유폴더
```

### 4.3 데이터 흐름
1. 스캔 → 파일 목록 및 메타데이터 수집 → SQLite 저장
2. 파서 → 각 파일에서 텍스트 추출
3. LLM → 텍스트 요약/분류/태깅 → 결과를 메타데이터에 병합
4. 임베딩 모델 → 텍스트를 벡터화 → 벡터DB 저장 (자연어 검색용)
5. 사용자 → 검색/탐색/승인 → 정리 실행 → 결과 파일시스템 반영

## 5. 화면 설계 (와이어프레임 개요)

### 5.1 대시보드
- 전체 스캔 현황(총 파일 수, 분석 완료율, 미분류 파일 수)
- 최근 분석된 문서 카드 목록(요약 미리보기)
- "새 인수인계 프로젝트 시작" 버튼

### 5.2 스캔/가져오기 화면
- 스캔 대상 폴더 선택(다중 폴더 지원)
- 제외 규칙 설정
- 스캔 진행률 바 + 실시간 로그
- 스캔 완료 후 "AI 분석 시작" 버튼(선택 실행)

### 5.3 자료 탐색기 (핵심 화면)
- 좌측: 카테고리/날짜별 트리 뷰
- 중앙: 파일 카드 목록(제목, AI 요약 1줄, 날짜, 태그 뱃지)
- 우측: 선택 파일 상세 패널(전체 요약, 유사 파일 목록, 원본 열기 버튼)
- 상단: 통합 검색창 + 필터(기간/카테고리/포맷)

### 5.4 AI 채팅 화면 (자료에게 질문하기)
- 채팅 인터페이스, 답변 시 근거가 된 원본 문서 링크 표시(출처 명시로 신뢰성 확보)
- 예시 질문 칩 제공("이 부서 주요 현안 알려줘", "최근 3개월 회의록 찾아줘")

### 5.5 정리 실행 화면
- AI 제안 정리 계획을 트리 형태로 미리보기 (Before/After 비교)
- 항목별 승인/제외 체크박스
- "복사로 정리" / "이동으로 정리" 선택
- 실행 후 결과 요약 리포트

### 5.6 인수인계서 생성 화면
- 표준 템플릿 선택
- 자동 채워진 초안 미리보기(섹션별 수정 가능한 에디터)
- HWP/DOCX로 내보내기 버튼

### 5.7 설정 화면
- Ollama 모델 선택/변경(gemma4:e2b 외 다른 로컬 모델도 선택 가능하도록 확장성 확보)
- 분류 카테고리 커스터마이징
- 민감정보 탐지 규칙 관리
- 데이터 백업/초기화

## 6. 기술 스택 제안

| 영역 | 제안 기술 | 사유 |
|---|---|---|
| 데스크톱 프레임워크 | Electron + React | 공무원 PC는 대부분 설치형 프로그램 필요, 웹뷰 기반으로 UI 개발 생산성 확보 |
| 백엔드/로직 | Python (FastAPI, 로컬 프로세스로 내장) | 문서 파싱·OCR·데이터 처리 생태계가 가장 풍부 |
| LLM 런타임 | Ollama (gemma4:e2b 기본, 확장 가능) | 완전 로컬 구동, 경량 모델로 일반 사무용 PC에서도 동작 가능 |
| 임베딩/벡터검색 | 로컬 임베딩 모델 + SQLite 확장(sqlite-vec) 또는 경량 Chroma | 별도 서버 없이 단일 파일 DB로 운용 가능 |
| 메타데이터 DB | SQLite | 설치 부담 없는 파일 기반 DB, 백업 용이 |
| HWP 파싱 | pyhwp/hwp5 계열, 필요 시 한글과컴퓨터 자동화 API | 국내 공공기관 문서의 다수가 HWP 포맷 |
| OCR | Tesseract(한국어 언어팩) | 스캔 문서·이미지 회의록 대응 |
| 문서 출력 | python-docx, HWP 변환 도구 | 인수인계서 표준 양식 출력 |

## 7. 개발 로드맵 (단계별 MVP 전략)

| 단계 | 범위 | 목표 |
|---|---|---|
| **Phase 1 (MVP)** | 파일 스캔, 메타데이터 추출, 기본 검색/탐색 UI | AI 없이도 "제목/날짜순 정리"만으로 즉시 체감 효과 제공 |
| **Phase 2** | Ollama 연동, 문서 요약·자동 분류·태깅 | 자료 파악 시간 단축 효과 본격화 |
| **Phase 3** | 자연어 검색(RAG), AI 채팅, 중복/버전 탐지 | 지식 탐색 능력 고도화 |
| **Phase 4** | 인수인계서 자동 생성, 민감정보 탐지 | 실제 업무 산출물까지 자동화 |
| **Phase 5(확장)** | 부서 단위 이력 축적, 다중 사용자 지원 | 개인 도구 → 조직 자산화 |

> MVP는 AI 없이도 동작해야 합니다. LLM 연동은 부가가치이지, 핵심 스캔/정리 기능이 LLM에 종속되면 안 됩니다(모델 오류·성능 이슈 시에도 기본 기능은 항상 동작해야 함).

## 8. 리스크 및 고려사항

| 리스크 | 내용 | 대응 방안 |
|---|---|---|
| 망분리/폐쇄망 환경 | 업무망은 인터넷이 차단된 경우가 많음 | 오프라인 설치 패키지 제작, 모델 파일도 사전 포함 배포 |
| HWP 파싱 정확도 | 비공개 바이너리 포맷으로 완벽한 파싱이 어려움 | 파싱 실패 시 "원본 열기 후 수동 태깅" 폴백 제공 |
| 경량 모델의 한계 | gemma4:e2b는 효율형 모델로 복잡한 추론엔 한계 | 프롬프트를 단순 작업 단위로 세분화, 필요시 더 큰 모델(E4B 등) 옵션 제공 |
| 원본 파일 손상 우려 | 자동 정리 과정에서 실수로 파일 유실 가능 | 기본값을 "복사" 정리로 설정, 실행 전 필수 미리보기·승인 단계 |
| 개인정보/기밀 노출 | 문서 내 민감정보가 인덱스에 그대로 저장될 위험 | 인덱스 DB 자체도 암호화, 민감정보 필드는 별도 접근 통제 |
| 사용자 신뢰 확보 | AI 분류 결과를 맹신하면 오분류 위험 | AI 제안은 항상 "제안"으로 표시하고 사람이 최종 승인하는 UX 원칙 고수 |
| 처리 성능 | 저사양 공무원 PC에서 대용량 폴더 처리 시 부하 | 백그라운드 비동기 처리, 배치 단위 분석, 진행률 표시 |

## 9. 요약

이 시스템의 핵심 경쟁력은 화려한 AI 기능이 아니라 **"신뢰할 수 있는 최소 기능(스캔·정리·검색)을 먼저 확실히 제공하고, 로컬 LLM은 그 위에 이해를 돕는 조력자로 얹는 것"**입니다. 특히 공직 환경의 제약(망분리, HWP, 개인정보보호)을 정면으로 반영해야 실제로 채택될 수 있는 도구가 됩니다. Phase 1(AI 없는 순수 정리 도구)만으로도 이미 상당한 시간 절감 효과가 있으므로, 이를 우선 완성한 뒤 AI 기능을 단계적으로 얹는 전략을 권장합니다.
