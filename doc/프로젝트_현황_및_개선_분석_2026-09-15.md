## 3. 최우선 수정 사항

### P0-1. 원본 수정 후 질문 근거와 날짜가 과거 상태로 남는다

**상태: 메모리 DB로 재현. 운영 전 수정 필요.**

- 스캐너는 변경된 문서의 해시와 파싱 상태를 갱신하지만, 기존 날짜·문서 임베딩·조각·조각 임베딩을 무효화하지 않는다.
- 파싱 단계는 문서 본문과 전문 검색 색인을 새로 쓴다. 이후 날짜 계산은 `eff_date IS NULL`, 문서 임베딩은 해당 모델의 벡터가 없는 문서만 처리한다.
- 질문 준비도 조각이 없거나 임베딩이 빠졌는지만 확인한다. 원본 변경 여부는 확인하지 않는다.
- 재현 결과: 전문 검색 본문은 `new content 2026`으로 바뀌었지만 질문 조각은 `old content`, 날짜는 `2023-01-01`로 남았다. 조각 재생성 대상도 0건이었다.

**영향:** 화면별로 서로 다른 버전의 내용을 보여주거나, 수정된 자료에 대해 과거 내용으로 답할 수 있다. 인수인계 신뢰성을 직접 훼손한다.

**개선:** 원본 해시를 각 분석 산출물과 연결하고, 내용 변경 시 자동 산출물을 순서대로 무효화·재생성한다. 사용자가 확정한 교정은 별도로 보존한다. 재색인 중에는 오래된 근거 사용 여부를 명확히 처리한다.

**완료 기준:** 동일 경로 파일의 내용과 날짜를 수정한 뒤 재분석하면 본문·질문 조각·벡터·자동 추정 날짜가 새 버전으로 맞고, 사용자 교정은 유지된다.

### P0-2. 사라졌다 돌아온 파일이 계속 ‘원본 없음’으로 남는다

**상태: 동일 크기·수정시각의 복귀 파일로 재현.**

- 스캐너가 동일 크기·수정시각이면 즉시 건너뛰므로 `upsert_document()`의 `missing_since = NULL` 경로를 타지 않는다.
- 재현 결과: 파일이 다시 발견됐는데도 `missing_since`가 남았다.
- 추가로 `_walk()`는 디렉터리 접근 오류를 무시한다. 전체 스캔이 불완전한 상황에서 발견되지 않은 파일을 일괄 ‘없음’ 처리할 위험이 있다.

**영향:** 외장 저장장치나 공유 폴더가 일시적으로 끊겼다가 복구돼도 자료가 계속 검색·분석에서 제외될 수 있다.

**개선:** 파일을 발견하면 내용 변경과 무관하게 존재 상태부터 복구한다. ‘삭제됨’, ‘자료원 연결 끊김’, ‘접근 실패’를 구분하고, 정상적으로 탐색을 마친 범위에만 사라짐 판정을 적용한다.

**완료 기준:** 삭제·복원, 공유 폴더 연결 끊김·복구, 하위 폴더 접근 거부에서 자료 상태가 올바르게 회복된다.

근거: `app/ingest/scanner.py:93`, `app/ingest/scanner.py:129`, `app/ingest/scanner.py:146`, `app/db/repo.py:253`.

### P0-3. 로컬 주소 검사만으로 외부 통신 차단을 보장하지 못한다

**상태: 앱 호출 코드와 설치된 HTTPX의 환경 프록시 경로 확인. 실제 외부 전송은 하지 않았다.**

- 앱은 목적지 호스트를 루프백으로 제한한다.
- 그러나 HTTP 호출에서 환경 프록시 사용을 끄지 않는다. 설치된 HTTPX는 기본적으로 환경 프록시를 신뢰한다.
- 모의 환경에서 `HTTP_PROXY`를 지정하고 `NO_PROXY`를 비우자 HTTP 프록시 경로가 구성됐다. 루프백 URL이라는 이유만으로 자동 배제되지 않는다.

**영향:** 해당 환경 설정이 있는 PC에서는 문서 내용이 포함된 생성·임베딩 요청이 프록시로 향할 가능성이 있다. 현재 PC에서 유출됐다는 의미는 아니다.

**개선:** 공통 HTTP 클라이언트에 `trust_env=False`를 적용하고 루프백 및 스킴 제한을 유지한다. 프록시 환경 변수가 있어도 직접 로컬 통신만 하는지 검증한다.

근거: `app/ai/client.py:88`, `app/ai/client.py:121`, `app/ai/client.py:163`, `app/ai/client.py:190`; 설치된 `.venv/Lib/site-packages/httpx/_api.py`, `_client.py`.

### P1-2. AI 모델 준비 상태 판정이 실제 호출 모델과 어긋난다

### P1-4. 실제 자료 평가와 대용량 검증이 부족하다

저장된 RAG 평가셋은 합성 자료에 맞춘 9개 질문이다. 기존 계획서에는 9/9 통과, 응답 중앙값 10.2~14.2초, 첫 질문 30.5초가 기록돼 있다. 이는 과거 기록이며 이번 측정 결과가 아니다. 구현의 유사도 임계값도 합성 자료 기준이다.

또한 질문마다 모든 조각 벡터를 읽고 행렬로 만들어 정규화한다. 문서 수가 아닌 조각 수로 비용을 계산해야 한다. 예를 들어 10만 조각 × 1,024차원 × 4바이트는 원시 벡터만 약 410MB이며, DB 결과와 중간 배열은 추가된다. 업무 군집화에는 전체 문서 간 비교와 군집별 큰 행렬 계산도 있다. 실제 메모리 초과나 시간 수치는 측정하지 않았다.

**권장 검증:** 비식별 실제 자료로 독립 평가셋을 만들고, 답해야 하는 질문·유보해야 하는 질문·충돌 문서·표·날짜·담당자·부정문을 포함한다. 첫 파일럿 기준으로 100개 이상의 질문, 3회 이상 반복, 1천·1만·5만 문서 규모별 처리 시간·최대 메모리·응답 p50/p95를 제안한다. 수치는 현재 성능이 아니라 검증 계획이다.

캐시, 범위에 맞춘 선행 후보 제한, 부분 정렬, 군집 통계의 블록 계산을 먼저 검토하고 측정 결과에 따라 검색 저장소를 교체한다.

근거: `tests/fixtures/rag_eval/cases.json`, `doc/질문화면_RAG_개선계획.md:700`, `app/search/rag.py:587`, `app/core/clustering.py:167`.

### P1-5. 배포와 운영 준비를 하나의 검증 절차로 묶어야 한다

- 의존성 잠금 검사: 현재 환경과 잠금 파일 일치 확인. 단, `start.bat`은 잠금 파일 대신 범위 지정된 `requirements.txt`로 설치한다.
- 저장소에서 CI 설정과 공통 pytest 설정 파일은 확인되지 않았다. 자동화가 외부에서 관리되는지는 미확인이다.
- 실행 의존성과 개발·테스트·빌드 의존성이 같은 설치 목록에 있다.
- PyInstaller 설정에는 프롬프트와 SQL만 데이터 파일로 지정돼 있고, 앱이 읽는 `app/ui/assets/logo.png`는 빠져 있다. 실제 배포물 표시를 확인해야 한다.
- DB 마이그레이션 백업은 구현돼 있으나, 사용자용 정기 백업·복구 흐름은 확인되지 않았다. 원본 복사와 분석 결과 백업을 구분한 복구 절차가 필요하다.
- 본문·요약 등이 담긴 DB는 암호화되지 않으며 UI가 이를 안내한다. 도입 환경의 저장 위치·접근 권한·반출 기준을 정해야 한다.

배포용 잠금 설치 → 전체 테스트 → 실행 파일 빌드 → 자체 점검 → 깨끗한 오프라인 Windows 환경 확인 → 복원 확인을 릴리스 기준으로 연결하는 것이 좋다.

### P2. 설명과 유지보수 구조를 정리한다

- README의 ‘완벽하게 파싱’, ‘100% 완전 로컬’ 표현을 검증 가능한 지원 범위와 설치 조건으로 구체화한다. OCR은 현재 MVP 범위 밖이며, HWP 3.0은 지원하지 않고 HWP 표 구조도 보존하지 않는다. 이 자체를 MVP 결함으로 보지는 않는다.
- 제품 기준서·PRD·개선 계획의 요구사항을 ‘구현됨 / 검증됨 / 미검증 / 보류’로 구분하는 표를 둔다.
- 약 1,500줄의 DB 저장소와 큰 질문 엔진을 변경 원인별로 나누고, 백그라운드 작업의 중복된 종료 처리를 공통화한다. 분리 자체보다 갱신 규칙과 트랜잭션 경계를 명확히 하는 것이 우선이다.
- 새 대메뉴를 늘리기보다 기존 화면에서 미확인 업무·근거 부족·사용자 확인 진행도를 잘 드러내고, 실제 후임자가 업무 파악에 걸리는 시간을 측정한다.

## 6. 검증 내역과 한계

- 현재 가상환경: Python 3.14.6. 잠금 파일 검사 통과.
