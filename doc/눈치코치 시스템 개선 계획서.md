## — 로컬 AI 기반 업무 인수인계·업무기억 복원 시스템

**문서 성격:** 제품 개선 방향과 단계별 적용 기록 (제품 범위는 00번 기준서 우선)

**대상 시스템:** `docs_mate / 눈치코치(NunchiCoach)`
**핵심 목표:** 범용 문서 AI가 아니라, ​**후임자가 전임자의 자료에서 업무를 빠르고 검증 가능하게 복원하는 전문 시스템** 확립

---

# 1. 개선 방향 요약

눈치코치은 향후 **“AI 문서 검색 프로그램”이나 “문서 챗봇”으로 발전해서는 안 된다.**

이 시스템이 지향해야 할 최종 모습은 다음과 같다.

> **전임자가 남긴 수천~수만 개의 업무 자료를 읽어, 후임자가 자신이 맡은 업무가 무엇인지(What), 언제 해야 하는지(When), 과거에는 어떻게 처리했는지(How)를 근거 문서와 함께 복원하고, 사람이 확인·교정한 결과를 다음 인수인계까지 지속적으로 축적하는 로컬 AI 기반 업무기억 시스템.**

현재 프로젝트 역시 이미 `파일 더미 → 업무 지도 → What · When · How`라는 상당히 명확한 정체성을 가지고 있으며, 검색·챗봇·일정 앱이 아니라 인수인계 문제 해결을 제품의 중심에 두고 있다. 이 방향은 그대로 유지해야 한다. 

향후 모든 기능은 다음 질문으로 판단한다.

> **“이 기능이 후임자가 What·When·How를 더 빠르고, 더 정확하게, 더 검증 가능하게 이해하도록 돕는가?”**

아니라면 우선순위를 낮춘다.

## 2.2 대표 메시지

### 메인 카피

**전임자 없이도, 자료가 업무를 설명합니다.**

### 설명

전임자가 남긴 파일을 분석해

# 3. 이 제품이 하지 않을 것

제품 정체성을 유지하기 위해 다음 영역으로 확장하지 않는다.

- 범용 ChatGPT형 AI 비서
- 일반 문서 작성 도구
- 일반 파일관리 프로그램
- 전자결재 시스템
- 기록물관리 시스템
- 업무 일정 직접 입력·관리 프로그램
- 범용 사내 통합검색 플랫폼
- 프로젝트 관리 도구
- 범용 LMS
- 범용 SOP 제작 프로그램

필요한 기능이 있더라도 반드시 **인수인계 목적에 맞게 축소·재해석하여 제공한다.**

예를 들어 “캘린더”를 만드는 것이 아니라 **자료에서 반복 업무 시점을 발견**하고, “SOP 편집기”를 만드는 것이 아니라 **과거 문서 흐름으로 업무 처리 순서를 복원**한다.

# 4. 핵심 사용자

## 4.1 Primary User — 후임 담당자

발령 또는 업무 변경 직후 다음 상황에 놓인 사람이다.

- 업무가 정확히 무엇인지 모른다.
- 폴더 구조를 모른다.
- 어떤 문서부터 읽어야 할지 모른다.
- 반복 업무 시기를 모른다.
- 과거 처리 절차를 모른다.
- 전임자에게 계속 질문하기 어렵다.

제품의 모든 기본 UI는 이 사용자를 기준으로 설계한다.

---

## 4.2 Secondary User — 전임 담당자

업무를 넘기기 전:

- 업무 분류를 확인한다.
- 대표 문서를 지정한다.
- 반복 시기와 처리 흐름을 확인한다.
- 잘못된 AI 결과를 수정한다.
- 인수인계 상태를 점검한다.

즉 전임자에게는 **“업무기억 정리 도구”​**가 된다.

---

## 4.3 Tertiary User — 관리자

향후 조직형 버전에서는:

- 인수인계 누락 업무
- 최신 자료가 없는 업무
- 담당자 확인이 안 된 업무
- 반복업무 관리 상태

등을 확인할 수 있다.

다만 관리자 기능을 초기 제품 전면에 두어서는 안 된다.

# 5. 제품의 핵심 경험

눈치코치은 다음 5단계 경험을 만들어야 한다.

### ① 자료를 연결한다

전임자의 PC 폴더, USB, 공유폴더 등을 등록한다.

↓

### ② 업무지도가 만들어진다

파일을 보는 것이 아니라:

> **당신이 인수받은 업무는 7개로 추정됩니다.**

를 먼저 보여준다.

현재 시스템이 이미 이 방향으로 설계되어 있으므로 핵심 철학으로 유지한다. 

↓

### ③ 업무 하나를 이해한다

업무 상세에서:

**What**  
이 업무가 무엇인가?

**When**  
언제 반복되는가?

**How**  
과거에는 어떤 순서로 처리했는가?

**Evidence**  
왜 그렇게 판단했는가?

를 한 흐름으로 이해한다.

↓

### ④ 사람이 확인한다

AI가 발견한 결과를:

- 확인
- 수정
- 합치기
- 나누기
- 제외
- 재분류

할 수 있다.

↓

### ⑤ 다음 인수인계를 준비한다

사람이 확인한 업무기억은 다음 담당자에게 그대로 이어진다.

이를 통해 제품을:

**일회성 분석 도구 → 조직의 지속적 업무기억 시스템**

으로 발전시킨다.

# 9. AI 결과 상태 체계

모든 AI 또는 알고리즘 결과에 동일한 상태 모델을 적용한다.

## 상태 1 — 확인됨

**✓ 담당자 확인**

사람이 직접 확인했다.

## 상태 2 — 자료 기반 추정

**◐ 자료에서 추정**

충분한 근거는 있으나 사람이 아직 검증하지 않았다.

## 상태 3 — 확인 필요

**△ 자료가 불충분**

근거가 약하거나 후보가 충돌한다.

## 상태 4 — 판정 불가

**○ 확인할 수 없음**

자료에서 판단할 수 없다.

---

이 상태 모델을:

- 업무 분류
- 날짜
- 반복 주기
- 처리 단계
- 최신본 후보
- AI 답변

전부에 동일하게 사용한다.

사용자는 제품 전체에서 새로운 신뢰 체계를 다시 배울 필요가 없다.

# 10. “추정”과 “사실”을 절대 혼합하지 않는다

특히 When과 How에서 가장 중요한 원칙이다.

현재 시스템은 반복 여부를 여러 연도 문서의 패턴으로 판단하며, 충분한 연도 자료가 없으면 반복을 주장하지 않는 보수적인 구조를 갖고 있다. 이 철학은 반드시 유지한다. 

하지만 UI를 한 단계 강화한다.

### 기존

`매년 9~11월 반복`

### 개선

**과거 자료에서 매년 9~11월 반복됨**

`2022·2023·2024·2025 자료에서 확인`

그리고 사용자가 승인한 이후:

**✓ 매년 9~11월 반복 업무**

가 된다.

즉:

> **AI가 지식을 만든다 → 사람이 지식을 확정한다**

라는 구조를 제품 전체에 적용한다.

# 11. 가장 중요한 신규 UX — 교정 시스템

향후 우선순위는 AI 생성 기능보다 **교정 UX**가 높아야 한다.

반드시 지원해야 하는 조작:

### 업무

- 업무 이름 수정
- 업무 설명 수정
- 업무 A+B 합치기
- 업무 하나를 두 개로 나누기
- 업무 삭제가 아니라 “업무 아님” 처리

### 문서

- 다른 업무로 이동
- 복수 업무와 연결
- 미분류 문서 직접 배정
- 대표 문서 지정

### 날짜

- AI 선택 날짜 수정
- 다른 후보 선택
- 날짜 직접 입력
- “날짜 모름”으로 확정

### When

- 반복 주기 확인
- 주기 수정
- 반복 아님
- 올해만 예외 처리

### How

- 단계명 수정
- 단계 순서 변경
- 단계 삭제
- 빠진 단계 추가
- 해당 단계 근거 문서 변경

사람이 수정한 값은 자동 재분석이 절대 덮어쓰지 않는다.

현재 DB 역시 이 원칙을 이미 반영하고 있으므로 UI를 그 수준까지 끌어올려야 한다.

**Claim → Evidence → Original**

이라는 3단계 검증 UX를 제품 전체에 통일한다.

# 16. RAG 검색 구조 개선

현재 RAG 구현은 임베딩 cosine similarity 상위 chunk를 직접 선택하는 비교적 단순한 구조이고, 코드 내 similarity threshold 역시 실자료 재조정이 필요한 임시 기준으로 명시되어 있다. 

목표 구조는 다음과 같다.

```text
질문
 ↓
질문 구조화
 · 업무
 · 연도/기간
 · 문서 유형
 · 키워드
 ↓
FTS 검색 + Vector 검색
 ↓
메타데이터 Filter
 ↓
완전중복 제거
 ↓
문서 다양성 확보
 ↓
Reranker
 ↓
Top Evidence
 ↓
LLM 답변 생성
 ↓
Claim-Citation 검증
 ↓
근거 없는 문장 삭제/유보
 ↓
화면 출력
```

특히 반드시:

**답변에 사용한 문서 목록 = citation**

이 아니라:

**개별 사실 문장 ↔ 실제 근거**

관계를 검증해야 한다.

# 18. 신규 핵심 기능 1 — 인수인계 모드

제품의 가장 중요한 신규 기능으로 권장한다.

눈치코치이 분석을 끝내고 사용자를 방치하지 않고:

> **“이제 무엇을 확인해야 하는가?”**

를 안내한다.

---

## 인수인계 진행 화면

업무 홈 일부에 표시한다.

```text
인수인계 진행도 72%

✓ 업무 7개 중 5개 확인
✓ 핵심문서 18개 중 12개 확인
◐ 반복 업무 5개 중 3개 확인
△ 처리 순서 4개 확인 필요
```

---

## 첫날

- 업무 목록 확인
- 잘못된 업무명 수정
- 핵심 문서 읽기
- 이번 달 업무 확인

## 첫 주

- 주요 업무의 과거 처리 순서 확인
- 반복 일정 확인
- 미분류 중요 문서 확인

## 완료

- 모든 주요 업무 확인
- 핵심문서 확인
- 반복업무 확인
- How 확인

이렇게 하면 프로그램을 단순 검색기가 아니라:

**“인수인계를 완료시키는 제품”**

으로 만들 수 있다.

# 19. 신규 핵심 기능 2 — 업무기억 건강도

업무별 지식 상태를 점검한다.

예:

```text
행정사무감사       양호
예산관리           확인 필요
계약관리           자료 부족
```

검사 항목:

- 업무 설명 존재
- 최근 핵심문서 존재
- 최근 연도 자료 존재
- 반복 주기 확인
- 처리 순서 확인
- 대표 문서 지정
- 담당자 검토
- 장기간 업데이트 없음 여부

---

## 활용

전임자가 떠나기 전:

> **“다음 담당자에게 넘기기 전에 무엇이 부족한가?”**

를 알려준다.

이 기능으로 눈치코치의 사용 시점을:

**발령 직후만 사용**

에서

**업무 수행 중 지속 사용 → 다음 인수인계 준비**

까지 확대한다.

# 20. 신규 핵심 기능 3 — 연도 비교

업무 상세에서:

```text
2024년
요구자료 → 취합 → 제출

2025년
요구자료 → 사전검토 → 취합 → 제출 → 추가질의
```

처럼 두 연도의 업무 흐름을 비교한다.

그리고:

> **2025년부터 ‘사전검토’ 단계가 추가된 것으로 보입니다.**

처럼 변화점을 제안한다.

단, 역시 근거 문서를 보여준다.

이 기능은 단순 검색 제품에서 쉽게 제공하기 어려운 눈치코치만의 차별화 기능이 될 수 있다.

# 21. 신규 핵심 기능 4 — 올해 처리 결과 반영

현재 시스템은 과거 자료로 How를 복원한다.

사용자가 올해 실제 업무를 수행하면:

> **“올해 처리 흐름으로 반영”**

버튼을 제공한다.

이를 통해 AI가 추정했던 과거 흐름을 실제 최신 업무 흐름으로 갱신한다.

장기적으로는:

**과거 기록에서 복원 → 사람이 수행 → 다시 업무기억으로 축적**

되는 순환구조를 만든다.

# 30. 보안 개선

Local-first는 중요한 경쟁력이지만, “외부 통신을 하지 않는다”만으로 보안이 완성되지는 않는다.

현재 DB에는 추출된 본문·chunk·검색 index가 저장되므로 프로젝트 DB도 사실상 민감정보로 취급해야 한다. 

필수 개선:

- 프로젝트 데이터 암호화
- 암호화 백업
- 프로젝트 완전삭제
- 임시파일 정책
- 로그 원문 저장 방지
- 모델 파일 hash 검증
- dependency lock
- SBOM
- 오프라인 installer
- 프로젝트 저장위치 권한 확인

# 31. 기술/AI 구조 원칙

# 40. 최종 제품의 차별화 문장

눈치코치이 최종적으로 만들어야 할 시장상의 차별점은 다음과 같다.

### NotebookLM과의 차이

> 문서에 질문하는 데서 끝나지 않고 **업무 구조를 자동 복원한다.**

### Glean/Enterprise Search와의 차이

> 모든 사내 지식을 찾는 것이 아니라 **새 담당자가 인수해야 할 업무를 이해시킨다.**

### 일반 RAG와의 차이

> 질문을 잘 답하는 것보다 **What·When·How를 구조화하는 것이 먼저다.**

### 파일관리 프로그램과의 차이

> 파일을 정리하지 않고 **파일에서 업무를 정리한다.**

### 일정관리 프로그램과의 차이

> 일정을 입력받지 않고 **과거 자료에서 업무 주기를 발견한다.**

### SOP 프로그램과의 차이

> 절차를 새로 작성하지 않고 **과거 업무 흔적에서 처리 흐름을 복원한다.**

### 클라우드 AI와의 차이

> 민감한 업무문서를 외부에 보내지 않고 **로컬에서 분석한다.**

# 41. 제품 비전

눈치코치의 최종 목적은 문서를 잘 찾게 만드는 것이 아니다.

> **“담당자가 바뀌어도 업무의 기억은 사라지지 않게 한다.”**

사람이 이동할 때마다 업무 노하우가 다시 초기화되는 문제를 해결하는 것이 제품의 장기 비전이다.

이를 위해 시스템은:

**파일 → 정보 → 업무 → 업무기억**

의 순서로 발전해야 한다.

초기에는 전임자가 남긴 파일에서 기억을 **복원**한다.

그 다음에는 사용자가 확인한 내용을 **지식화**한다.

그리고 실제 업무를 수행하면서 바뀐 내용을 **갱신**한다.

마지막에는 다음 담당자가 그 기억을 다시 **인수**한다.

```text
전임자의 자료
     ↓
AI가 업무기억 복원
     ↓
후임자가 확인·교정
     ↓
실제 업무 수행
     ↓
최신 업무기억 축적
     ↓
다음 담당자에게 전달
     ↓
업무기억이 끊기지 않음
```

이 순환이 완성될 때 눈치코치은 단순한 AI 애플리케이션이 아니라 **조직의 업무 연속성을 지켜주는 시스템**이 된다.

# 42. 최종 의사결정 원칙

향후 기능을 추가할 때 다음 순서로 평가한다.

**1. 업무 이해를 빨라지게 하는가?**

**2. What·When·How 중 하나를 더 잘 설명하는가?**

**3. 근거를 확인할 수 있는가?**

**4. 틀렸을 때 사용자가 쉽게 고칠 수 있는가?**

**5. 사용자 교정이 다음 분석에 남는가?**

**6. 로컬·읽기전용·보안 원칙을 지키는가?**

위 질문 중 여러 개가 NO라면 개발 우선순위를 낮춘다.

눈치코치은 기능이 많은 AI 프로그램보다,

> **“이 프로그램을 켜면 내가 맡은 업무를 빠르게 이해할 수 있다.”**

라는 한 가지 경험을 압도적으로 잘 만드는 제품을 지향해야 한다.
