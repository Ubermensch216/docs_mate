# 질문 화면 RAG 개선 계획

**대상:** `app/search/rag.py` · `app/ui/views/ask.py` · `app/core/chunking.py` · `app/jobs/pipeline.py`
**작성 근거:** 실제 프로젝트 DB(문서 77건·조각 263개)와 살아 있는 Ollama(`gemma4:e2b` + `bge-m3`)로 직접 질의해 측정한 결과
**목표:** *등록한 자료만 근거로, 문장마다 출처가 붙고, 근거가 없으면 답하지 않는* 질의응답

---

## 0. 확정된 방향 (사용자 결정)

| 항목 | 결정 |
|---|---|
| 대화 방식 | **단발 질의 + 명시적 후속질문 버튼.** 멀티턴 기억을 만들지 않는다(기준서 §17). 버튼은 이전 맥락을 암묵적으로 기억하는 대신 **완성된 새 질문**을 생성한다 |
| 유보 정책 | **모를 때 모른다고 한다.** 근거가 약하면 답하지 않고 찾은 문서만 보여준다 |
| 응답 시간 | **지금(15~40초)보다 빨라야 한다.** 목표 10초 이내. 재정렬·검증은 **규칙 기반**으로 하고 생성 호출은 질문당 1회를 유지한다 |

이 세 결정이 이후 설계를 모두 규정한다. 특히 응답 시간 결정 때문에 **LLM 재정렬(rerank)과 LLM 기반 근거 검증은 채택하지 않는다.** 개선계획서 §16이 제시한 파이프라인 중 그 두 단계만 규칙으로 대체한다.

## 1. 실측 — 지금 무슨 일이 일어나는가

실제 자료로 네 개 질문을 던진 결과다. 추정이 아니라 관측이다.

### 측정 1. 인용이 근거가 아니다

```
Q: 2025년 행정사무감사 때 뭘 제출했어?
A: 제출 자료는 2025년 행정사무감사 제출자료 및 의원질의 답변 관련 자료입니다.
   [1], [2], [3], [4], [5], [6], [7], [8]
```

네 질문 **모두** 인용이 정확히 8건이었다. `TOP_K = 8`과 같다. [rag.py:122](app/search/rag.py:122)가 모델이 실제로 무엇을 썼는지와 무관하게 **컨텍스트 전량을 인용으로 붙이기** 때문이다.

> 개선계획서 §16이 명시적으로 금지한 방식이다.
> "**답변에 사용한 문서 목록 = citation**이 아니라 **개별 사실 문장 ↔ 실제 근거**"

사용자는 지금 아무것도 검증할 수 없다. 8개 중 어느 것이 그 문장의 근거인지 알 방법이 없다.

### 측정 2. 중복본이 근거 자리를 독점한다

```
Q: 수질통계는 언제 작성해?
근거: 2025_..._최종2.csv · 2025_..._수정.csv · 2025_..._진짜최종.csv ·
      2025_..._최종.csv · 2023_....csv · 2024_..._송부.csv ·
      2023_....csv · 2023_..._복사본.csv
```

근거 8건이 **사실상 같은 문서의 사본**이다. 근거 예산 전부를 한 문서에 써 버렸다.

DB에는 이미 `documents.hash`와 `duplicate_groups` 뷰가 있고, When·How는 [repo.py:437](app/db/repo.py:437)에서 대표본만 고르는 서브쿼리를 쓴다. **RAG만 이 장치를 쓰지 않는다.**

### 측정 3. 질문 속 조건이 무시된다

```
Q: 작년 예산 요구자료는 누가 만들었어?
A: 전년도(2024년) 자료를 참고하여 동일한 절차로 진행하였다 [1][2][4][5]
근거: 2025_예산…, 2022_예산…, 2023_예산…, 2023_행정사무감사…, 2022_행정사무감사…
```

"작년"이 연도 조건으로 쓰이지 않았고, 다른 업무(행정사무감사) 문서까지 섞였다. 답변 문장은 **다른 문서에 있던 문장을 그대로 옮긴 것**이라 질문에 답하지 못했다. `questions.filters` 열은 있지만 [rag.py:60](app/search/rag.py:60) `ask()`가 필터를 받지 않는다.

### 측정 4. 무관한 자료로도 답을 만든다 — 가장 위험

```
Q: 계약관리 업무는 어떤 순서로 처리해?
A: 제시된 자료에는 계약관리 업무의 처리 순서에 대한 구체적인 정보는 포함되어
   있지 않으나, 분기별 처리건수와 완료율은 다음과 같습니다.
   | 구분 | 1분기 | 2분기 | 3분기 | 4분기 |
   | 처리건수 | 41 | 38 | 45 | 39 | …
근거: 전부 월간실적보고_실적취합.xlsx
```

계약관리를 물었는데 **월간실적보고 숫자로 표를 지어냈다.** 모델 스스로 "정보가 없다"고 말하고도 답을 만들었다. `MIN_SIMILARITY = 0.30`이 걸러 내지 못했고, 무엇보다 [ask.md:14](app/ai/prompts/ask.md:14)가 이렇게 지시한다.

> "부분적으로만 관련 있어도 answered=true입니다."

이 문구는 v1의 반대 문제(좋은 답을 만들고도 false로 표시)를 고치려고 넣은 것인데, 반대편으로 과하게 넘어갔다.

### 측정 5. 문서 하나가 영구히 보이지 않는다

```
2025_행정사무감사_요구자료접수_최종2.docx — 조각 9개 중 9개 미임베딩
meta.chunks_checked = '1'
```

가장 최신 행정사무감사 문서, 즉 후임자가 **가장 먼저 물어볼 문서**가 질문 화면에서 통째로 빠져 있다. [shell.py:278](app/ui/shell.py:278)의 재개 판정이 `chunks_checked` 플래그만 보기 때문에, 한 번 플래그가 서면 미임베딩 조각을 다시 시도하지 않는다. 다른 단계들은 플래그가 아니라 **실제 문서 상태**로 남은 일을 판정하는데([shell.py:264](app/ui/shell.py:264)) 이 단계만 다르다.

### 측정 6. 조각이 너무 잘다

| 항목 | 값 |
|---|---|
| 조각 길이 중앙값 | **34자** |
| 50자 미만 조각 | 166 / 263 (63%) |
| 최대 | 209자 |

[chunking.py](app/core/chunking.py)가 `document_sections`의 문단 하나를 조각 하나로 그대로 쓰고 **하한이 없다**. 상한(1200자)만 있다. 그래서 실제 조각은 이렇다.

```
[3] 3문단 (9자)  '문서유형: 보고서'
[4] 4문단 (18자) '작성일: 2022. 11. 12.'
[8] 8문단 (15자) '붙임: 관련 근거자료 1부.'
```

9자짜리 조각의 임베딩은 의미를 담지 못한다. Top-8을 다 모아도 컨텍스트가 300자 남짓이라 **모델에게 답할 재료 자체가 없다.** 측정 1의 답변이 내용 없이 맴돈 이유가 이것이다.

> 주의: 이 수치는 현재 DB가 합성 표본 위주라 실제 기관 자료보다 과장돼 있을 수 있다. 다만 *하한이 없다*는 구조적 결함은 실자료에서도 그대로다 — 공문의 `붙임:`, `작성일:` 같은 짧은 문단은 실제로도 흔하다.

### 측정 7. 그 밖

- **FTS를 쓰지 않는다.** `document_fts`(trigram)가 이미 있고 문서 화면은 쓰는데([documents.py:254](app/ui/views/documents.py:254)) RAG는 벡터만 쓴다. "2025년 제출자료", 문서번호, 고유명사처럼 **정확히 일치해야 하는 질의**에 약하다.
- **응답 시간** 첫 질문 40.8초, 이후 15~17초. 첫 질문이 유독 느린 것은 생성 모델 적재 때문이다(임베딩 모델과 서로 밀어낸다 — [client.py:35](app/ai/client.py:35)에 이미 관측 기록이 있다).

## 1-C. R3(하이브리드 검색) 완료 — 전후 비교 실측

```
python -m app.tools.rag_report
```

| 지표 | R2 후 | R3 후 |
|---|---|---|
| 통과 | 5/8 | 5/8 (불변) |
| 유보 정확도 | 0/3 | 0/3 (불변 — 예상대로, R3 범위 밖) |
| 응답 정확도 | 5/5 | 5/5 |
| 근거 다양성 | 0.98 | 0.98 |
| 응답 시간(중앙값) | 15.8초 | 16.0초 |

**이 평가셋에서는 R3가 지표를 움직이지 않았다.** 솔직하게 기록한다. 이유는 두 가지다.

1. `exact-term` 사례("부서별자료요청 문서는 언제 만들어졌어?")는 R2 단계에서 이미 순수 벡터 검색만으로 통과하고 있었다. `bge-m3` 임베딩이 한국어 고유명사도 의미적으로 잘 포착해서, 이 작은 합성 코퍼스에서는 하이브리드 검색이 구제할 "벡터가 놓치는 사례"가 실제로 없었다.
2. 나머지 미통과 3개(`wrong-task-hallucination`·`absent-topic`·`absent-person`)는 전부 유보 정확도 문제다. R3는 **검색 정밀도**를 다루지 검색 자체를 안 해야 하는 상황(지어내기)을 다루지 않는다 — R5·R6의 몫이다.

**그렇다고 R3가 무의미하지는 않다.** 하이브리드 메커니즘이 실제로 작동하는지는 전용 단위 시험(`test_exact_term_match_counts_as_strong_even_below_similarity_threshold`)으로 별도 검증했다 — 질문 벡터와 **직교하는**(코사인 유사도 0) 벡터를 가진 조각이라도, 질문의 고유명사가 본문에 정확히 있으면 FTS가 구제해 근거로 채택됨을 확인했다. 이 경로는 이번 합성 코퍼스에는 없지만, 실제 기관 자료에서 문서번호·부서명·고유명사가 본문과 파일명에는 있고 의미적으로는 특별히 가깝지 않은 경우(짧은 공문, 서식화된 표 등) 값을 발휘할 것으로 예상한다. R1 평가셋에 이런 사례를 추가하는 것을 R4 이후 과제로 남긴다.

부수적으로 `escape_match`의 AND 결합(문서 화면 키워드 검색에는 맞음)을 자연어 질문 문장에 그대로 썼다면 거의 항상 실패했을 것 — 조사·어미가 섞인 문장 전체 단어가 원문에 그대로 있을 리 없기 때문이다. 조각 검색 전용으로 `escape_match_any`(OR 결합)를 따로 만들어 이 문제를 피했다. 실제로 이 문제를 시험이 잡았다(문서 하단 §구현 메모 참고).

**솔직하게 말하면, 이 평가셋에서 R4는 통과 개수를 늘리지 못했다.** R3가 이미 `year-scope`·`relative-year` 두 사례를 (연도 필터나 중복 제거 없이) 우연히 통과시키고 있었다. R4가 노린 것은 바로 이 두 메커니즘의 **정확성**이었지, 이 특정 평가셋의 통과 개수가 아니었다 — 그리고 그 메커니즘이 실제로 옳게 동작하는지는 구현 과정에서 발견한 두 개의 진짜 회귀와, 그것을 잡아낸 시험으로 확인됐다.

### 회귀 1 — FTS "강한 근거" 판정이 순위를 무시했다

`2025년 행정사무감사 때 뭘 제출했어?` 질문에 무관한 `수질통계`·`월간실적보고` 문서가 근거로 섞였다. 원인: `escape_match_any`의 OR 결합은 토큰 하나만 맞아도 걸리는데, 이 코퍼스의 모든 2025년 문서는 상투 문구 "본 문서는 2025년 …"를 공유한다. bm25 자체는 이런 흔한 토큰만 맞은 문서를 순위 뒤쪽(18~38위)으로 정확히 낮게 매겼는데, `strong_ids |= set(fts_ranked)`가 **순위 전체(40위 깊이)를 무차별로 "강함"으로 처리**하면서 그 순위 정보를 버렸다.

**수정:** `fts_ranked[:TOP_K]`만 강한 근거로 인정한다 — FTS 엔진 자신의 최상위 판단만 신뢰하고, 40위 깊이 풀 전체를 이진 플래그로 쓰지 않는다.

### 회귀 2 — 연도 필터가 더 나은 다른 연도 후보를 밀어내고 빈 자리를 약한 동일연도 후보로 채웠다

`작년 예산 요구자료는 어떤 내용이야?` 질문에서 "작년"이 2025로 올바르게 해석됐다. 그런데 연도 필터가 2022~2024년의 **더 관련 있는** 예산관리 문서(유사도 0.55~0.65)를 전부 제외시키면서, 우연히 2025년인 **무관한** 행정사무감사 문서(유사도 0.51~0.56, 그래도 `MIN_SIMILARITY=0.30`은 넘음)가 빈 TOP_K 자리를 채웠다. 연도 필터도 대표본 중복 제거도 "완전히 사라지면 되돌린다"는 안전장치는 있었지만, **"일부만 사라지고 빈 자리가 남으면 무한정 깊이 채운다"**는 문제까지는 막지 못했다.

**수정:** `EXPLORATION_WINDOW = TOP_K * 2`를 도입해, 대표본 판정·연도 필터·다양성 상한이 후보를 걸러낼 때 이 깊이보다 아래는 빈 자리를 메우는 데 쓰지 않는다. 그 결과 `relative-year` 사례는 근거 3건(문서 2종)만 내고 멈춘다 — **근거가 적게 나가는 것이 엉뚱한 근거가 나가는 것보다 낫다**는 원칙을 그대로 코드로 옮긴 것이다.

두 회귀 모두 `python -m app.tools.rag_report`가 아니라 **실제 프로젝트 DB로 직접 추적**해서 찾았다 — 오프라인 단위 시험만으로는 이런 다단계 상호작용(FTS 순위 + 다양성 상한 + 연도 필터가 겹치는 지점)을 재현하기 어려웠다. 두 회귀 모두 이후 되돌아가지 않도록 회귀 시험을 추가했고(`test_generic_token_buried_deep_in_fts_does_not_become_strong_evidence`, `test_year_filter_does_not_reach_past_the_exploration_window_for_filler`), 수정 전 코드로는 실제로 실패하는지 되돌려 확인했다.

### 실제로 개선된 것

- **`duplicate-flood`의 근거 구성이 바뀌었다.** 여전히 8건 모두 수질통계 문서지만, 이제 2023~2025년에 걸쳐 서로 다른 8개 문서에서 나온다(전에는 2025년 사본 위주로 몰렸다).
- **인용 전량 나열이 8/8 → 6/8로 줄었다.** `relative-year`(8→3건)와 `duplicate-flood`가 더 이상 무조건 `TOP_K`개를 채우지 않는다 — 근거가 실제로 걸러지고 있다는 신호다.
- **응답 시간이 16.0초 → 7.6초로 줄었다.** `EXPLORATION_WINDOW`가 탐색 범위를 좁혀 `_select_context`의 SQL 조회 대상이 줄어든 부수 효과로 보인다. 의도한 최적화는 아니었지만 R8(응답 시간)에 긍정적이다.

### 남은 3개 실패는 전부 R4 범위 밖이다

`wrong-task-hallucination`·`absent-topic`·`absent-person` — 셋 다 유보해야 하는데 답을 만든 사례다. R4는 검색 정밀도(무엇을 근거로 쓸지)를 다루지, 지어내기 자체를 막지 않는다. R5(문장별 근거 검증)·R6(프롬프트 v3)의 몫이다.

## 1-E. R5(문장별 근거 검증) 완료 — 이 계획의 핵심, 가장 큰 폭의 개선

```
python -m app.tools.rag_report
```

| **유보 정확도** | 0/3 | **2/3** |
| 응답 정확도 | 5/5 | 5/5 |
| 인용 전량 나열 | 6/8 | **1/6** |

### 구현

- `app/ai/schemas.py`의 `ASK_SCHEMA`를 `{answered, answer}`에서 `{answered, sentences: [{text, sources}]}`로 바꿨다. 문장과 근거를 모델이 직접 짝짓게 강제한다.
- `app/search/verify.py` 신설 — 규칙 기반, 생성 호출 추가 없음(원칙 6). 근거 없는 문장, 존재하지 않는 근거 번호를 인용한 문장, 인용한 근거에 없는 숫자를 쓴 문장, 인용한 근거와 어휘가 거의 안 겹치는 문장을 버린다.
- `_compose_answer()` — 검증에서 살아남은 문장만으로 답변을 조립하고, 근거 번호를 실제로 쓰인 것만 `[1][2][3]`으로 다시 매긴다. 원래 `TOP_K` 번호에 구멍이 생겨도(예: 2번이 버려짐) 사용자에게는 `[1][5][7]`처럼 듬성듬성 보이지 않는다.
- `_salvage_ask_response()` — R1이 찾은 JSON 잘림 버그(§1-A)를 여기서 처리했다. `num_predict`를 500→900으로 올리고, 그래도 잘리면 정규식으로 완성된 문장 객체만 건져 답변이 통째로 사라지는 것을 막는다.
- `client.generate_json()`이 이제 원문(raw)도 함께 돌려준다(2-튜플 → 3-튜플). 스키마마다 잘림 복구의 뜻이 다르므로 이 계층은 스키마를 모른 채 원문만 넘기고, 판단은 호출자(`rag.py`)가 한다. `analyze.py`의 4개 호출부는 원문을 쓰지 않고 그대로 버린다.

### 유보 정확도가 0/3에서 2/3로 오른 이유

**프롬프트 문구는 전혀 건드리지 않았다.** v2의 "부분적으로만 관련 있어도 answered=true"는 그대로다(R6에서 다룰 몫). 그런데도 `absent-topic`·`absent-person` 두 사례가 저절로 유보로 돌아섰다 — 모델이 "정보가 없습니다"라고 말하면서도 함께 붙인 문장(예: "다만 예산요구액과 집행액이 다음과 같이…")이 검증에서 **근거 없음** 또는 **어휘 불일치**로 걸러졌고, 그 결과 살아남은 문장이 하나도 없어 자동으로 유보 처리됐다. answered=true인데도 근거가 다 걸러지면 유보한다는 규칙이 프롬프트의 허술함을 규칙으로 보완한 셈이다.

### 남은 실패 하나 — `wrong-task-hallucination`은 R5로 못 잡는다, 예상대로

```
Q: 계약관리 업무는 어떤 순서로 처리해?
A: 구분별 처리건수는 1분기 41건, 2분기 38건, 3분기 45건, 4분기 39건입니다.[1]~[8]
근거: 전부 월간실적보고 문서
```

이 문장은 **검증을 전부 통과한다.** 41·38·45·39라는 숫자가 실제로 인용한 월간실적보고 조각 안에 그대로 있고, 어휘도 그 표 내용과 겹친다 — R5의 네 검사(근거 존재·유효 번호·숫자 근거·어휘 중첩) 모두 "문장이 자신이 인용한 근거에 충실한가"만 본다. 이 사례의 진짜 문제는 **인용한 근거 자체가 질문과 무관하다**는 것이고, 이건 검색 단계(무엇을 강한 근거로 볼지, R3·R4·R7)와 프롬프트(관련 없으면 애초에 답하지 말라, R6)의 몫이다. 정확히 계획했던 R5의 한계이며, 처음부터 R6·R7이 이어받기로 되어 있었다.

### R6에서 밝혀진 것 — 이 표의 숫자들은 단일 실행이라 신뢰도가 낮다

R6에서 같은 프롬프트로 같은 평가셋을 두 번 돌렸더니 1회차 7/8, 2회차 8/8이 나왔다. **이 문서의 §1-A~§1-E에 적힌 모든 수치는 단일 실행 결과이므로, 사례 하나 차이는 개선이 아니라 편차일 수 있다.** 지표의 큰 흐름(유보 정확도 0/3 → 2/3, 인용 전량 나열 7/7 → 1/6)은 유효하지만, 세부 사례 하나하나의 통과·실패는 §1-F 이후처럼 `--repeat`로 재야 한다. 이 교훈으로 `rag_report`에 `--repeat` 옵션을 추가했다.

### 응답 시간이 크게 늘었다 — R8이 반드시 다뤄야 한다

중앙값 7.6초 → **27.6초**, 최대 32.9초. `num_predict` 500→900(문장 배열 스키마의 구조적 오버헤드 + 잘림 방지)이 주 원인으로 보인다. R2(조각 재설계)도 같은 방향으로 응답 시간을 늘린 바 있다(11.8→15.8초) — 정확도를 올릴 때마다 속도가 희생되는 패턴이 누적되고 있다. **R8에서 반드시 상쇄해야 한다**: 질문 화면 진입 시 모델 예열, 임베딩 행렬 캐시, 그리고 `GEN_TOKEN_BUDGET`이 실제로 900까지 필요한지 R1 평가셋의 실제 응답 길이 분포로 재확인.

## 2. 목표 구조

개선계획서 §16의 파이프라인에, 위 실측과 세 가지 결정을 반영한 형태다.

```
질문 + scope(업무·기간·자료원)
  ↓ ① 질문 구조화        연도/업무/문서유형/키워드 — 규칙 우선
  ↓ ② 하이브리드 검색     FTS5(정확 일치) + 벡터(의미) → RRF로 순위 결합
  ↓ ③ 메타데이터 필터     scope + 질문에서 뽑은 연도·업무
  ↓ ④ 중복 제거          hash 대표본 (When·How와 같은 기준)
  ↓ ⑤ 문서 다양성        문서당 최대 2조각
  ↓ ⑥ 이웃 확장          앞뒤 조각을 붙여 문맥 복원
  ↓ ⑦ 재정렬             규칙: 최신 연도 · '최종/송부' 표기 · 질의어 일치
  ↓ ⑧ 생성 1회           문장 단위 + 문장별 근거 번호를 스키마로 강제
  ↓ ⑨ 근거 검증          규칙: 지지되지 않는 문장은 삭제
  ↓ 화면                 문장별 [n] · Evidence Preview · 명시적 후속질문
```

**②~⑦과 ⑨는 전부 규칙 기반이다.** LLM 호출은 ⑧ 한 번뿐이라 응답 시간이 지금보다 늘지 않는다(원칙 1·6, 그리고 응답 시간 결정).

## 3. 구현 단계

착수 순서는 **의존성 순서가 아니라 위험 순서**다. 평가셋을 먼저 만든다 — 없으면 이후 모든 변경이 추측이 된다.

### R0. 색인 무결성 (선행, 작음)

측정 5의 결함. 다른 것을 아무리 고쳐도 문서가 안 보이면 소용없다.

- [shell.py:276](app/ui/shell.py:276) `needs_chunks` 판정을 `chunks_checked` 플래그 대신 **실제 상태**로 바꾼다 — 같은 파일 `pending` 질의가 이미 쓰는 방식이다.
  ```sql
  -- 조각은 있는데 임베딩이 없는 문서가 남아 있는가
  SELECT 1 FROM chunks c LEFT JOIN embeddings e ON e.chunk_id = c.id
  WHERE e.chunk_id IS NULL LIMIT 1
  ```
- 질문 화면 준비 상태에 실제 수치를 노출한다 — [ask.py:120](app/ui/views/ask.py:120) `_readiness()`가 지금은 `chunks_embedded == 0`만 본다. "질문 준비 254 / 263"처럼 보이면 사용자가 빠진 것을 안다.

### R1. 평가셋과 계측 (모든 개선의 자)

- `tests/fixtures/rag_eval/` — 질문 · 정답 근거(doc_id + locator) · 정답 유형(답변 가능/유보해야 함) 쌍. **유보해야 하는 질문을 반드시 포함한다** — 측정 4가 그것을 못 잡는 결함이었다.
- `app/tools/rag_report.py` — [dating_report.py](app/tools/dating_report.py)·[parse_report.py](app/tools/parse_report.py)의 CLI 리포트 패턴을 그대로 따른다.
- 측정 지표
  | 지표 | 현재(실측) | 목표 |
  |---|---|---|
  | 근거 Top-5 적중률 | 미측정 | 기준선 확보 후 설정 |
  | 근거 없는 문장 비율 | 사실상 100%(인용이 전량 나열) | 0% |
  | 유보해야 할 질문의 유보율 | 0/1 (측정 4 실패) | 100% |
  | 근거 문서 다양성 | 1문서/8인용 (측정 2) | 문서당 ≤2 |
  | 응답 시간(2번째 이후) | 15~17초 | ≤10초 |

### R2. 조각 재설계 (측정 6)

`app/core/chunking.py`

- 인접 섹션을 **목표 400~800자 창**으로 병합한다. locator는 범위로 남긴다(`"1~5문단"`) — 근거 위치를 잃지 않는다.
- **표·시트·슬라이드는 병합하지 않는다.** 구조 자체가 의미이고 locator가 셀 범위를 가리켜야 한다.
- 임베딩에 넣는 텍스트에만 문서 제목·연도를 접두한다. 화면에 보여 줄 인용문은 원문 그대로 유지한다 — 사용자가 원본에서 찾을 수 있어야 한다.
- **재색인이 필요하다.** 스키마 마이그레이션(§3.7)에서 chunks·embeddings를 지우고 다시 만든다.

### R3. 하이브리드 검색 (측정 7)

- `app/search/fts.py` 신설 — [documents.py:254](app/ui/views/documents.py:254)의 trigram + LIKE 폴백 로직을 **추출해 공유**한다. `schema.sql:95` 주석이 이미 이 파일의 존재를 전제하고 있다.
- **`chunk_fts` 추가(스키마 v3).** 현재 `document_fts`는 문서 단위라 어느 조각이 일치했는지 알 수 없다. 조각 단위 정확 일치가 RAG 정밀도의 핵심이다.
- 두 순위를 **RRF(Reciprocal Rank Fusion)** 로 합친다. 점수 스케일이 다른 둘을 합치는 표준적이고 규칙만으로 되는 방법이다.

### 1. 근접 중복 축약 — R6에서 넘어온 실패를 푼 열쇠

`app/search/rerank.py`의 `collapse_near_duplicates()`. hash 기반 대표본 판정은 **파일 전체**가 같아야 걸리는데, 표 한 장만 같고 나머지가 다른 문서 여덟 개가 그 판정을 피해 근거 자리를 전부 차지하고 있었다. 파일이 아니라 **내용**으로 접는다(공백·줄바꿈 차이는 무시).

### 2. 규칙 재정렬

`rerank()` — '먼저 읽을 문서'(`core/scoring.py`)가 이미 검증한 `FINAL_MARKERS`를 그대로 재사용한다. 같은 자료를 두고 화면마다 다른 기준으로 순위를 매기면 사용자가 "업무 화면에서는 이게 먼저인데 질문 근거에는 왜 저게 먼저지?"를 겪는다. 가중치는 RRF 점수에 **비례해** 얹는다 — RRF는 절대값이 0.016 근처라 1.0짜리 보너스를 더하면 검색 순위가 통째로 무의미해진다.

### 3. `MIN_SIMILARITY` 실측 보정 (0.30 → 0.40)

옛 임시값 0.30은 **아무것도 거르지 못했다** — 대부분의 질의에서 138개 조각이 전부 그 선을 넘었다. 평가셋 9개의 최고 유사도를 재 보니 갈리는 지점이 보였다.

```
답해야 하는 질문   0.490 ~ 0.672
유보해야 하는 질문 0.316 ~ 0.474
```

0.40은 두 무리 사이에 놓이되 답해야 하는 쪽과 0.09의 여유를 둔다. 다만 **합성 표본 138조각·질문 9개로 잡은 값**이라, 실제 기관 자료로 파일럿할 때 같은 방법으로 다시 재야 한다.

### 4. 이웃 확장 — 그리고 그것이 만든 회귀

평가 사례를 먼저 만들어 필요한지 **측정한 뒤** 구현했다. `table-needs-context`("2023년 예산 요구액이 얼마야?")는 답이 표 조각(`[집계] 예산요구액 820`)에만 있는데 그 표에는 연도도 업무명도 없다 — 그 정보는 이웃 문단에만 있다. 이웃 없이는 0/3 실패였다.

그런데 이웃 확장을 켜자 **`wrong-task-hallucination`이 3/3에서 0/3으로 되돌아갔다.** 무관한 월간실적보고 표에 이웃 문단이 붙자, 그 전에는 "자료가 부족하다"고 옳게 유보하던 모델이 그 숫자로 답을 만들어 냈다. 이웃 확장은 **관련 있는** 근거를 설명 가능하게 만드는 장치이지 무관한 근거를 풍부해 보이게 하는 것이 아니므로, 질의어와 무관한 이웃은 붙이지 않도록 했다.

그 관문도 처음에는 새지 않았다 — "업무"처럼 **어느 공문에나 있는 낱말**이 통과시켰기 때문이다. 문서 빈도로 변별력을 재어(절반 넘는 문서에 나오면 버림) 해결했다.

### 5. 이 단계에서 잡은 잠재 결함 셋

전부 **실제 질의를 추적하다** 발견했고, 오프라인 시험만으로는 드러나지 않았을 것들이다.

**① 숫자 검증이 문장부호를 숫자로 셌다.** `_NUMBER` 정규식이 `"820,"`을 통째로 숫자로 잡아, 근거에 `820`이 있는데도 "없는 숫자를 썼다"며 정상 문장을 버렸다. 숫자 뒤에 쉼표가 오는 문장은 흔하므로 **광범위하게 오작동하고 있었다.**

**② 검증이 이웃을 근거로 인정하지 않았다.** 모델에게 이웃 조각을 문맥으로 보여주고서, 그 이웃에 있는 사실을 썼다는 이유로 문장을 버렸다 — 앞뒤가 맞지 않는다. **같은 문서 안의** 컨텍스트 조각까지 사실 확인 범위로 넓혔다(다른 문서로 넓히면 A를 인용하고 B의 숫자를 쓴 문장까지 통과해 검증이 무의미해진다).

**③ 한국어 조사 문제를 세 번째로 만났다.** R3(FTS AND 결합), R7(재정렬 질의어 대조), R7(검증 어휘 중첩) — 매번 같은 원인이었다. `app/core/korean.py`로 뽑아 세 곳이 같은 규칙을 쓰게 했다. 네 번째를 막기 위한 것이다.

### 남은 것

응답 시간 중앙값 11.8초 · **최대 41.7초**. 목표(10초 이내)에 아직 못 미치고 최댓값이 특히 나쁘다 — R8의 몫이다.

---

## 1-H. R8(응답 시간) 완료 — 계획의 가정이 틀렸던 단계

### 먼저 쟀다. 그리고 계획이 지목한 두 가지가 무의미했다

계획서 R8은 세 가지를 지시했다: 모델 예열, **임베딩 행렬 캐시**, 토큰 한도 재확인. 고치기 전에 단계별로 시간을 쟀다(평가셋 9개 전체).

| 단계 | 합계 | 비중 |
|---|---|---|
| **생성** | **130.63초** | **95%** |
| 임베딩 | 6.11초 | 4% (첫 호출 3.29초 = 모델 적재) |
| 행렬 적재 | **0.03초** | 0.02% |
| FTS | 0.01초 | — |
| 선별 | 0.01초 | — |

**임베딩 행렬 캐시는 구현하지 않았다.** 계획서는 "매 질문마다 전체를 DB에서 다시 읽어 정규화하므로 1만 건에서는 문제가 된다"고 적었는데, 실제로는 0.03초다. 지금 규모에서 고쳐 봐야 얻을 것이 없고, 코드만 복잡해진다. 조각 수가 크게 늘면 그때 다시 재고 결정한다 — 재는 도구는 이미 있다.

**토큰 한도(900)도 병목이 아니었다.** 느린 사례의 실제 생성량은 509~560토큰으로 한도에 닿지 않는다.

### 진짜 원인 — 모델이 근거마다 같은 문장을 하나씩 썼다

느린 두 사례를 열어 보니 원인이 분명했다.

```
Q: 수질통계는 언제 작성해?   (조각 8개 → 509토큰 → 40초)
  · 2025년 수질통계 … 2025년 7월 … '분기 수질통계' 단계에서 작성되었다.
  · 2025년 수질통계 … 2025년 10월 … '분기 수질통계' 단계에서 작성되었다.
  · 2025년 수질통계 … 2025년 4월 … '분기 수질통계' 단계에서 작성되었다.
  … (조각 수만큼 반복)
```

**속도만의 문제가 아니다.** 이 질문의 답은 여덟 문장이 아니라 "분기마다(1·4·7·10월) 작성한다" 한 문장이어야 한다. 느린 이유와 답이 나쁜 이유가 같았다.

프롬프트 v6에 "같은 사실을 말하는 조각은 한 문장으로 합치고 sources에 번호를 모두 넣으라"를 넣었다.

| 지표 | R7 후 | R8 후 |
|---|---|---|
| 통과 (3회 반복) | 9/9 | **9/9 (유지)** |
| 유보 정확도 | 3/3 | 3/3 |
| 응답 시간 중앙값 | 11.8초 | **10.2초** |
| 응답 시간 **최대** | **41.7초** | **24.7초** |

답변도 나아졌다 — `task-scope`가 9문장(38.9초)에서 2문장(16.1초)이 됐다.

```
담당부서는 관련 자료를 취합하여 기한 내 제출하였다.[1][2][3][4]
전년도 자료를 참고하여 동일한 절차로 진행하였다.[1][2][3][4]
```

### 모델 예열 — 첫 질문 68.5초 → 30.5초

콜드 상태(모델을 내린 뒤)에서 직접 쟀다.

```
예열 없음:  첫 질문 68.5초
예열 있음:  모델 적재 21.3초(사용자에게 안 보임) + 첫 질문 30.5초
```

`WarmupRunner`가 질문 화면이 답할 준비를 마친 시점에 **한 번만** 돈다(`app/jobs/ask_task.py`). 사용자가 질문을 타이핑하는 동안 모델이 올라오므로 그 시간이 보이지 않는다. 실패해도 조용히 넘어간다 — 예열은 편의일 뿐이고, 안 되면 평소처럼 첫 질문이 느릴 뿐이다.

### 남은 것

중앙값 10.2초로 목표(10초 이내)에 사실상 닿았지만 **최대 24.7초**는 여전히 길다. 생성이 95%인 구조상 더 줄이려면 컨텍스트를 줄이거나(TOP_K 하향 — 근거 다양성과 상충) 더 작은 모델을 쓰는 수밖에 없다. 둘 다 정확도를 깎으므로, 실제 기관 자료로 파일럿한 뒤 사용자가 어느 쪽을 원하는지 보고 결정하는 것이 맞다.
